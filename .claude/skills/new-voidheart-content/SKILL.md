# New VoidHeart content

Each new block or item touches many files, and a missed one usually fails silently: no drop, a raw translation key, a missing tooltip. Past features needed follow-up requests for exactly these parts. Go through the sections that apply, and report any you skip with the reason.

Paths use `J/` for `src/main/java/net/voxelindustry/voidheart/` and `R/` for `src/main/resources/`. Before starting, find the most similar existing content and search the repo for its id to see every file it touches:

```bash
grep -rliE 'ravenous_relay|RAVENOUS_RELAY|RavenousRelay' src
```

## Block

- **Register** in `J/common/setup/VoidHeartBlocks.java` with `registerBlock`. It also creates the block item, adds it to the creative tab, and adds blocks with `requiresCorrectToolForDrops()` to the pickaxe tag during datagen.
- **Blockstate and block model** from `J/data/provider/ModelsProvider.java`, or hand-written in `R/assets/voidheart/` when the shape needs it.
- **Item model** generated by default. If it's hand-written, add the id to `HAND_WRITTEN_ITEM_MODELS` in `ModelsProvider`.
- **Item appearance:** check that it looks like the placed block. For a GeckoLib block, the item should be a still version of the block model. Follow `RavenousCollectorItemRender`, which needed two fixes before it was right.
- **Loot table:** a block without one drops nothing. Prefer `J/data/provider/BlockLootsProvider.java` for simple drops. Most existing blocks have hand-written tables in `R/data/voidheart/loot_table/blocks/`, which also suits drops that need custom rules.
- **Texture:** edit with the Aseprite CLI, starting from an existing texture so it matches the mod's style. 26.3 chooses a block's chunk layer from texture transparency, so a placed block's texture must be opaque unless the block should be translucent.

## Block entity

- **Register** in `J/common/setup/VoidHeartTiles.java` and extend SteamLayer's `TileBase`.
- **Renderer:** register in `J/VoidHeartClient.java` and use the `voidheart-rendering` skill.
- **Saved state:** save and load every field that must survive a reload, and sync what the client draws. Assume saved data can be stale or inconsistent, because unrepresentable portal states have corrupted worlds before (`eb4e848`).
- **Contents when broken:** decide whether they drop, stay on the item or are lost. To keep them on the item, follow `RavenousStorageBlock` and `RavenousStorageBlockItem`: `getDrops`, `setPlacedBy`, a data component in `VoidHeartDataComponents` and a tooltip. An empty block should drop a plain item so it still stacks.
- **Jade tooltip:** add a provider in `J/compat/jade/` and register it in both `register` and `registerClient` of `VoidHeartJadePlugin`. Add the `config.jade.plugin_voidheart.<name>` translation too. `RavenousRelayProvider` is a good template.

## Blocks that join structures or networks

Barriers, portals, Oculus Tables and relays share state across blocks, and this is where merge and redstone bugs have appeared. Check each of these, with unit tests for the pure logic as in `BarrierConfigTest`:

- Merging two configured structures keeps their settings.
- Breaking a middle block splits the structure correctly.
- The state survives a world reload.
- Redstone reaches the shared state from any block in the structure.

## Item

- **Register** in `J/common/setup/VoidHeartItems.java`.
- **Model** generated by `ModelsProvider`, or hand-written and listed in `HAND_WRITTEN_ITEM_MODELS`.
- **Texture** in `R/assets/voidheart/textures/item/`, made with the Aseprite CLI.

## Entity

Register in `J/common/setup/VoidHeartEntities.java` and the renderer in `VoidHeartClient`. The Shoulder Eye commit `7a911e9` shows the full set of parts, including model, render state, textures, particle and damage type.

## Recipes

- **Altar and Shatter Forge recipes** belong in `J/data/provider/RecipesProvider.java`, through `offerAltarRecipe` and `offerShatterForgeRecipe`. Don't hand-write these, since they were moved to datagen on purpose.
- **Other crafting recipes** are hand-written in `R/data/voidheart/recipe/` or use families in `RecipesProvider`. Follow the nearest example.
- **Reachability:** make sure a player can actually obtain the new content unless the user wants it creative-only.
- **New recipe types** need a REI category and display in `J/compat/rei/`, with registration in both `VoidHeartREIPlugin` and `VoidHeartREICommonPlugin`. Existing types appear in REI automatically.

## Translations

`R/assets/voidheart/lang/en_us.json` is hand-maintained, so add keys for the block or item, tooltips, Jade labels, config options and screens. Keep its LF line endings. The commit `7a911e9` flipped them and turned a 14-line change into a 217-line diff, so check `git diff --stat` after editing.

## Config

Put values players may want to tune in `J/common/config/VoidHeartConfig.java`, with translations for the YACL screen. Ask if it isn't clear which values should be exposed.

## Datagen

Generated files in `src/main/generated/` are committed. After changing a provider or registering something it covers, run this and commit the output with the change:

```bash
./gradlew runDatagen --console=plain
```

Check `git status` afterward. Unrelated generated changes mean something else is out of date, so mention them rather than quietly including them.

## Tests

- Put pure logic in unit tests under `src/test/`.
- Use the `verify-in-game` skill for anything placed, drawn, clicked or crafted. Include breaking the block and checking its drop, plus the item in hand and in the inventory.

## Report

End with the content's status against these sections, listing what was added, what doesn't apply, and what is still unverified in the game.
